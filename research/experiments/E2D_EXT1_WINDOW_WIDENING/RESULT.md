## Adversarial check on this result specifically

The concern before trusting this PASS: `select_roots`/`closure` are pure,
already-validated functions of a window's time bounds, and are inherently
monotonic in range — a wider window can only match more roots, never fewer.
That means "superset" holding here could be trivially guaranteed by E2D's
already-proven mechanism, without the widening *controller* (generation
bump, supersession, outcome carry-forward — the actual new code in this
extension) doing anything correct at all.

Checked directly: added a root (`E-VENDOR-4-TOO-LATE`, admitted
2026-08-25) outside even the widened window's end (2026-08-22), and
confirmed it is correctly *excluded* from generation 2's affected set,
while `E-VENDOR-3` (admitted 2026-08-20, inside the widened range) is
correctly included. This confirms the boundary check is real and doing
work, not a test that would pass regardless of correctness.

## What this does not test

Named in `PLAN.md` and repeated here so it isn't silently forgotten:
overlapping windows from different incident reports (union-at-evaluation),
`LEGACY_UNKNOWN` timestamp fallback, and huge/manifest-based parent lists.
None of the three are run in this pass.

## Scope

Same scope limit as E2D itself: this validates the design's widening
behavior on a constructed fixture. It does not touch `custody/*.py` and
does not establish that a real incident-correction workflow (a human
filing a wider report through whatever UI/API would exist) behaves this
way end-to-end.
