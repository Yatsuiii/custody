# E2D-EXT2 Result — Overlapping Windows From Separate Incident Reports

**Verdict: PASS.** All 8 checks in `PLAN.md` hold: two independent window
records (`W1`, `W2`) on the same source, activated separately, correctly
union at evaluation — a record affected by either is blocked, a record
affected by both is blocked once, each window's own closure is

Full detail in `result.json`, generated by `run.py`.

## Adversarial check on this result specifically

The sharpest claim here — `gap_record_unaffected` — could pass either
because the mechanism is correct, or because the test fixture happens not
to exercise the failure mode at all. Checked directly: built a deliberately
broken controller whose root selection treats all active windows as one
*merged* interval (earliest start to latest end) rather than a true
per-window union — exactly the bug this test exists to catch, since it's
the natural shortcut an implementation might take ("just track the min
start and max end across active windows"). Under that mutation,
`E-GAP-1`'s effective cap comes out `NONE` (wrong — it should be `ACT`,
since it falls in the real gap between the two windows). The actual
mechanism under test gives `ACT`. Confirms the check would fail loudly on
the specific bug it's named for, not just on this particular fixture by
accident.

## What this does not test

`LEGACY_UNKNOWN` timestamp fallback and huge/manifest-based parent lists
remain untested after this extension too.

## Scope

Same scope limit as E2D and E2D-EXT1: validates the design on a
constructed fixture, does not touch `custody/*.py`, does not establish
that a real multi-incident workflow (two different people filing two
different reports through whatever UI/API would exist) behaves this way
end-to-end.
