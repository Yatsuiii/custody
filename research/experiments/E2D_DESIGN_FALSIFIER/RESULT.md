## A real bug found and fixed during this run, reported rather than hidden

The first execution reported PASS. Before accepting that, the mechanism
was adversarially probed rather than trusted on a first green result — the
project's own stated discipline (`RESEARCH.md`: "we'd have shipped wrong
if we'd trusted the first version that worked").

**What was found:** `RevocationController.effective_cap` returned the
original bound `ACT` cap for an affected record during the gap between a
revocation window's intent being activated and its repair plan being
computed — a real violation of `DYNAMIC_TRUST_MODEL.md` step 2 ("gateways
... compute effective authority against active windows. A stale or
unavailable generation fails closed for consequential actions"). The
original crash/replay probe for exactly this gap (`after_intent_before_plan`)
never actually queried `effective_cap` during the gap itself — it only
checked state after the simulated crash had already resumed and completed,
so it silently passed a mechanism that failed open for the actual race it
was named after.

**The fix:** `effective_cap` now returns `NONE` for every record while any
active window has no plan yet, or a plan still at phase `INTENT` — not just
for records a not-yet-computed closure would name. Confirmed by direct
query (not just the automated metric) that both an affected record
(`E-VENDOR-2`) and an outside-window sibling (`E-BENIGN-1`) correctly read
`NONE` during that gap, then correctly return to their real state once the
plan resolves. The probe harness was also fixed to check `effective_cap`
at the actual crash point, not after resume.

## Mutation testing: does the falsifier actually have teeth

Two mutation tests were run against working code, not written in advance,
to check whether the metrics would actually catch two of the specific
failure modes `REPAIR_SEMANTICS.md` and `DYNAMIC_TRUST_MODEL.md` name:

1. **Forbidden shortcut** ("pruning support in place" — re-meeting an
   affected record's cap from its surviving parents instead of blocking it
   whole). A controller subclass implementing exactly this shortcut was
   run against the same fixture: `effective_cap` for `E-SYN-ACT-ACT`
   returned `ACT`, and `false_act_permits` correctly went from 0 to 1.
   Caught.
2. **Mechanism ignores active windows entirely.** A controller subclass
   whose `effective_cap` never consults `self.windows` at all was run
   against the same fixture: `false_act_permits` correctly went from 0 to
   2. Caught.

An earlier, flawed first attempt at mutation test 1 tampered a field that
was already correctly `ACT` before any window activated, so it proved
nothing — recorded here rather than silently redone, since a mutation test
that doesn't actually mutate the failure mode it claims to test is exactly
the kind of vacuous-pass risk this whole exercise exists to catch.

## What this does and does not establish

**Does establish:** a fully-specified, deterministic mechanism (no LLM,
network call, embedding, or fuzzy match anywhere in `run.py`) can satisfy
every safety and selectivity property the design's own preregistered gate
requires, on the frozen scenario, including under four simulated crash
points. The specific identified-in-advance failure modes (forbidden
re-meet shortcut, window-blind mechanism, fail-open race) were checked to
actually be catchable, not merely assumed absent.

**Does not establish:**
- Production readiness. The design doc's own "required outcomes" and
  `TRUSTED_COMPUTING_BASE.md` name concrete production blockers (e.g.
  `load_memory`'s text-hash reconnection, Memory Bank's server-side
  summarization not exposing source record ids) that this experiment does
  not touch — this fixture's receipts are fixture-constructed, not routed
  through those real paths.
- Behavior on any scenario outside the six frozen elements. One fixture,
  one PASS. Real fleets will hit shapes this fixture does not construct
  (huge retrieval manifests, schema evolution, overlapping/superseding
  windows, `LEGACY_UNKNOWN` timestamps) — each has its own named
  requirement in the design docs, none exercised here.
- That this is ready to fold into the Custody hackathon submission's
  shipped claims. `custody/*.py` was not touched by this branch and the
  submission's live proofs (G1-G5) say nothing about this mechanism.
  Folding a PASS-on-one-fixture research result into product claims
  without a separate, harder integration effort would be exactly the kind
  of overclaim `RESEARCH.md` already warns against once ("calling this
  paper-grade today would overclaim").
