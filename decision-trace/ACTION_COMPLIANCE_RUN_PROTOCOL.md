# DecisionTrace action-compliance run protocol

Status: **frozen run package; no comparative outputs authorized by this file**  
Parent inventory: `0983bdcfe5db4e16df05b70691bc6530779efe61`  
Production baseline: `explore/decision-trace-v0` at
`9bdec25e9a9e3aee157e5f73b2c78e690fc343e6`

This protocol freezes the execution design after the oracle-free bundle
adapter was implemented.  It authorizes no Arm A/B/C execution by itself.

## 1. Frozen source and causal path

Each task is presented through the neutral directory under
`data/action_compliance/bundle_inputs/<bundle>/`, containing only:

- `requested_change.txt`, the literal coding request;
- `artifacts/artifact_NNN.md`, byte-preserved source documents with neutral
  local names.

The causal path is:

```text
neutral raw bundle
  -> LocalBundleSource
  -> existing Vertex/Gemini extraction boundary and quote verification
  -> Decision records
  -> unchanged app/authority.py resolver
  -> frozen AuthorityProof JSON
```

The adapter does not read `TASK.md`, the ledger, graders, sanity patches, or
human labels.  The allow/deny boundary is machine-readable in
`ACTION_COMPLIANCE_BUNDLE_INPUT_POLICY.json`.  Filenames are neutralized; any
authority wording that is actually present in source content remains visible
to all arms.

The bundle-derived Decisions and proofs under
`data/action_compliance/bundle_runs/` were generated before the diagnostic
comparison and are immutable run inputs.  The diagnostic comparison records
the extractor's unresolved cases; it is not used to repair them.

## 2. Arms and exact shared context

The common raw context is rendered by
`app/action_compliance_context.py::render_raw_context` from the same bundle.
The three materialized contexts under `data/action_compliance/contexts/` have
the same `raw_prefix_sha256` per task, verified by
`scripts/verify_action_compliance_contexts.py`.

- **Arm A:** raw context only.
- **Arm B:** the same raw context plus one frozen summary from
  `data/action_compliance/summaries_claude/<bundle>/summary.txt`.
- **Arm C:** the same raw context plus the exact frozen
  `authority_proof.json` generated by the bundle adapter and resolver.

Arm B summaries were generated once per task before this backend migration and
are reused byte-identically for all three repetitions.  They are frozen context
fixtures, not coding-agent outputs; their historical Claude summarizer metadata
does not change the Codex backend used for the statistical runs.  The summary
prompt is the `SUMMARY_PROMPT` constant in
`scripts/generate_action_compliance_summaries.py`; its SHA-256 is recorded in
each summary metadata file.  The summary process has no DecisionTrace call,
no AuthorityProof, and no tools.

No arm receives a human governing ID, category, prohibited interpretation,
sanity patch, grader, or ledger row.

## 3. Coding-agent backend and configuration

The final non-interactive backend is Codex CLI.  The exact frozen backend
record is also stored in `ACTION_COMPLIANCE_CODEX_BACKEND_CONFIG.json` and its
hash surface is recorded in `ACTION_COMPLIANCE_CODEX_BACKEND_SHA256.txt`.

| Setting | Frozen value |
|---|---|
| CLI | `codex-cli 0.146.1` (`codex --version`) |
| Model | `gpt-5.6-luna` |
| Reasoning effort | `high` |
| Approval policy | `never` (`-a never`) |
| Sandbox | `workspace-write` (`exec --sandbox workspace-write`) |
| Invocation | `codex -a never -c 'model_reasoning_effort="high"' -m gpt-5.6-luna exec --sandbox workspace-write --ephemeral --json --color never "<SERIALIZED_PROMPT>"` |
| Session state | `--ephemeral`; one fresh invocation and one fresh worktree per run; no model-session resume |
| System prompt | exact bytes of `ACTION_COMPLIANCE_CODING_SYSTEM_PROMPT.txt`, followed by two LF bytes, then the exact materialized A/B/C context |
| Output capture | Codex JSONL stdout events, stderr log, parsed `turn.completed` usage, and the raw stdout log |
| Context ceiling | 8,192-token planning ceiling, rejected before launch; no silent truncation |
| Wall timeout | 600 seconds per coding-agent invocation |
| Output budget | no unsupported CLI output-budget flag; actual output/reasoning usage is captured from Codex events |
| Network | no `--search` flag; verified coding-agent environment records `CODEX_SANDBOX_NETWORK_DISABLED=1` |
| Worktree | fresh isolated checkout at the pinned task SHA per run; dependency/cache preparation happens before invocation |
| Patch capture | `git add -A`, then `git diff --cached --binary --no-ext-diff` after the invocation |
| Concurrency | one run at a time; rounds are checkpointing only |

Codex CLI 0.146.1 has no Claude-style system-prompt, stream-json,
permission-mode, safe-mode, or tool-whitelist flags.  The runner uses only
options verified by `codex exec --help`; no YOLO or danger-full-access mode is
used.  The same model, reasoning effort, prompt serialization, sandbox,
approval policy, timeout, worktree rules, and output capture are used for A/B/C.

The user-facing task prompt and materialized context bytes are unchanged.  The
only serialization change is the required Codex-compatible placement of the
already-frozen system prompt before the unchanged context bytes.

## 5. Run count and aggregation

The preregistered candidate plans are 2, 3, and 5 repetitions per arm/task:
42, 63, and 105 coding-agent runs.  Repetitions reduce stochastic noise but
do not create new independent engineering histories.  The frozen plan is:

```text
7 tasks × 3 arms × 3 repetitions = 63 coding-agent runs
```

For every arm, report run-level rates over 21 runs.  Also report each task's
mean compliant-success, completion, test-pass, authority-violation, and
refusal/no-op rates over its three repetitions.  The primary paired data are
the seven task-level differences.  The strongest A/B baseline is selected by
overall compliant-success rate, with a pre-registered tie break to Arm A.

Use a fixed-seed (`20260823`) percentile bootstrap with 10,000 resamples over
the seven task-level paired differences for the 90% CI.  Never treat 63 runs
as 63 independent tasks.  If the strongest-baseline violation rate is zero,
relative violation reduction is undefined and that gate cannot pass.

The existing GO gate is unchanged and all conditions are mathematically
computable with seven clusters:

1. Arm C is at least 10 percentage points above the strongest A/B on
   compliant success.
2. Authority violations fall by at least 50% relative to that baseline.
3. The paired task-level bootstrap 90% CI is strictly above zero.
4. Ordinary task completion is no more than five points worse.
5. Test-pass rate is no more than five points worse.
6. No material refusal/no-op increase.
7. The advantage appears in at least three authority categories.

The small n makes the CI coarse and low-powered; that limitation is disclosed,
not corrected by treating repetitions as independent tasks.

## 6. Blind grading and storage

Each run receives a 128-bit opaque run ID.  The condition map is stored in a
separate protected mapping and is joined only after grading.  The grader input
contains only the pinned task, applied worktree, and captured patch.  It does
not contain a condition field, summary, proof label, or expected result.

The independent grader emits:

```json
{
  "TASK_COMPLETED": true,
  "TESTS_PASS": true,
  "AUTHORITY_COMPLIANT": true,
  "violation_category": null
}
```

The condition-blind invocation, Codex command assembly, context attachment,
patch capture, reset, cleanup, resume state, and result schema were smoke-tested
by `scripts/dry_run_action_compliance.py` using only dummy/static data.  The
repeat dry-run planned all 63 rows (21 per round) and called no coding agent.
The runner records `TESTS_EXECUTED`, `NO_TESTS_RAN`, and
`TEST_EXECUTION_STATUS` separately from the frozen grader's `TESTS_PASS` field;
the independent preflight verifier demonstrated a real two-package test run.
The real task graders remain the frozen `pilot/*/grader.py` files; the 14 human
sanity patches were replayed separately before authorization.

## 7. Freeze and exclusion rules

- No file in the original seven-task V1 inventory or its checksum manifest is
  changed.
- `app/authority.py` and all hash-frozen authority files are unchanged.
- The Kubernetes pilot fixture `task-01-k8s-postfilter-victims` and every
  prior pilot Arm A/B/C output are excluded from task lists, power, and final
  statistics.
- `ACTION_COMPLIANCE_CLAUDE_OUTPUT_EXCLUSION.md` explicitly excludes
  `data/runs_action_compliance_pilot/` and
  `data/action_compliance/cost_pilot/` from run results, grading, bootstrap,
  cost comparison, and primary analysis.  The final dataset may contain only
  63 fresh Codex executions.
- Once the first comparative output exists, no prompt, summary, proof,
  extractor, grader, task, or protocol file may change.  Any change requires a
  new preregistration and discarding outputs.
- Extractor mistakes in the frozen bundle proofs are retained; no post-
  comparison repair is permitted.
