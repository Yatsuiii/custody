# Current

The applicable design is **PEP 723** (Final status), which replaces PEP 722 (artifact_002, https://peps.python.org/pep-0723/). A metadata block starts with `# /// TYPE`, ends with `# ///`, and contains comment-prefixed content. The standardized `script` type holds TOML with a top-level `dependencies` field—a list of PEP 508 requirement strings—plus optional `requires-python` and `[tool]` fields. Multiple blocks of the same type are an error; unclosed blocks are ignored (artifact_002). The task adds `src/pip/_internal/req/script_metadata.py` with `read_script_dependencies(scriptfile: str) -> list[str]`, returning dependencies in source order and raising `ValueError` for missing or malformed blocks, plus a unit test in `tests/unit/test_script_metadata.py` (raw task).

# History

**PEP 722** was rejected on 2023-10-21 and superseded by PEP 723 (artifact_001, https://peps.python.org/pep-0722/). It proposed a `# Script Dependencies:` marker followed by comment lines holding PEP 508 strings. Pip issue #12891 requested PEP 723 support; PR #13052 ("Support installing requirements from inline script metadata (PEP 723)") merged on 2025-11-27, closing that issue and adding a dedicated PEP 723 parser with functional tests (artifact_003, https://github.com/pypa/pip/issues/12891, https://github.com/pypa/pip/pull/13052, merge commit 36987b0c31b97ffb9fb7949ded628e9a6b10c016). The pinned task SHA b35182d8f7245f046eed2975275c57b54ce3ba56 is the pre-implementation snapshot (artifact_003).

# Scope

The task **intentionally extracts only dependencies**, excluding validation of `requires-python` and `[tool]` (artifact_002). Wiring the parser into pip's CLI is **explicitly out of scope** (raw task). PR #13052 is a neighboring implementation that added a PEP 723 parser and functional tests (artifact_003).

# Uncertainty

The sources do not establish: (1) whether PR #13052's parser overlaps with the requested `script_metadata.py` module or differs in location/interface; (2) whether the pinned SHA already contains partial implementation; (3) which TOML parsing library to use; (4) granular error-handling rules distinguishing malformed TOML from a missing block; (5) whether to support the rejected PEP 722 format for backward compatibility.
